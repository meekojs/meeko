# Releasing Meeko

The public repository is `meekojs/meeko` and the npm package is `@meekojs/meeko`. The CLI keeps the name `meeko`. Since `1.0.0`, versions follow the [stability policy](stability.md):

- a patch only fixes issues;
- a minor adds API or deprecates it with a documented replacement;
- only a major breaks compatibility or removes deprecated features.

Every change is recorded in the [CHANGELOG](../../packages/meeko/CHANGELOG.md) before publishing. Earlier `0.x` versions could change the API in a minor.

## Pre-release verification

In a clean copy of the commit to be published:

```powershell
pnpm install --frozen-lockfile
pnpm run verify
pnpm run e2e
node packages/meeko/node_modules/playwright-core/cli.js install chromium firefox webkit
pnpm run pilot:e2e
pnpm run package:smoke
pnpm -F meeko-language run package:vsix
pnpm -F meeko-language run test:host:isolated
npm pack ./packages/meeko --dry-run --json
```

The root `pnpm run …` commands forward to `packages/meeko` (`pnpm -F @meekojs/meeko run …`); `verify` also checks the Chrome extension (`pnpm -F meeko-devtools-extension run check`).

`pilot:e2e` checks SSR and hydration in Chromium, Firefox and WebKit during development and from the production build. `package:smoke` installs the tarball in a temporary project outside the monorepo and checks the CLI, SSR, TypeScript declarations, Vite and a project generated with `meeko init`. The npm package includes only `dist`, `README.md`, `LICENSE`, `CHANGELOG.md` and `package.json`; it excludes examples, tests, logo variants and local files. Before uploading a version, review the output of `npm pack --dry-run --json` to confirm that list.

## Publish the Meeko packages

The proposed `1.8.0` release is **unpublished**. The six public packages are `@meekojs/meeko`, `@meekojs/i18n`, `@meekojs/icon`, `@meekojs/ui`, `@meekojs/eslint-plugin` and `@meekojs/prettier-plugin`, in that order. `meeko-docs`, `meeko-docs-content`, `meeko-language` and `meeko-devtools-extension` are private and are not published to npm. Extensions retain their own versions.

Aligning all six at `1.8.0` allows one tag check for the whole release and avoids using new UI with core 1.7. The number does not constitute a new stability audit; the stability policy applies. The user must approve this decision. To keep the five new packages at `0.1.0`, change their manifests and changelog headings, this guide and the migration, and replace the version checks in `publish.yml` and `scripts/publish-packages.ps1` with an explicit version map before tagging. Keep core 1.8 and the `>=1.8 <2` ranges.

Finish and integrate the design program and resolve the open scrypt hash question in `docs/reference/commands/meeko-auth-hash.md` before publishing. Repeat all gates on the final commit: `pnpm build`, `pnpm check`, `pnpm test:packages`, `pnpm -F @meekojs/ui test`, `pnpm -F @meekojs/i18n test`, `pnpm package:smoke`, `pnpm package:workspace-smoke`, and the earlier verification steps. `pnpm package:workspace-smoke -Offline` works without network if the store contains all dependencies. Inspect real tarballs, including `.d.meeko.ts` declarations, Inter and its OFL, and the absence of test data or local paths.

`pnpm format:check` has known formatting debt, but **neither `ci.yml` nor `publish.yml` invokes it**. It does not directly block these workflows; CI does run `pnpm lint`. `.woodpecker/web.yml` does run `pnpm format:check` in `gates`, and `images`/`release` depend on it: formatting debt blocks that web pipeline. Fix formatting in a separate validated change before deployment; retain the gate. Do not silence gates or run a global autofix: format release files only and address global cleanup separately. Also check branch protection and required checks on GitHub.

### First publication of new packages

A package must exist on npm before configuring its trusted publisher, so `@meekojs/i18n`, `@meekojs/icon`, `@meekojs/ui`, `@meekojs/eslint-plugin` and `@meekojs/prettier-plugin` are published once from the maintainer's interactive session. **`@meekojs/meeko` does not go through this:** its versions carry signed provenance and publishing one by hand would lose it. `publish-first.ps1` leaves any package that already exists on npm to the workflow, even if it only has versions under `next`: what counts is its root document, not a dist-tag. Never save tokens or OTPs in files or arguments. Use Node 24+ and npm **11.5.1 or later** (the workflow pins 11.19.0).

1. Approve contents and versions; confirm ownership or publication rights for the `@meekojs` scope and run `npm login` yourself.
2. Integrate the release commit into `main` with green `test` and `redis-integration` on that SHA, under its ruleset, and update your checkout with `git fetch origin`.
3. Run `pwsh -NoProfile -File scripts/publish-first.ps1` from a clean checkout. It only prepares tarballs with `pnpm pack` and runs `npm publish --dry-run`; it checks the session and the state of all six versions on the registry. A network or authentication error stops the process: it never means a version is absent.
4. Only after explicit publication authorization, run `pwsh -NoProfile -File scripts/publish-first.ps1 -Execute`, which requires the commit to be on `origin/main`. npm asks for authentication or an OTP on the console, once per package if needed. It stops at the first error and shows which versions reached npm.
5. If it stopped halfway, fix the cause and run `scripts/publish-first.ps1 -Execute -Resume`, which skips what is already published. The workflow cannot resume this: it rejects packages that do not exist on npm yet, because they have no trusted publisher.
6. On npm, configure a GitHub Actions Trusted Publisher **for each of the six packages**: owner `meekojs`, repository `meeko`, workflow `publish.yml`, environment `npm`. Confirm that the one for `@meekojs/meeko` uses exactly that environment. Check `npm trust list <package>` from your session. Do not add publication tokens to GitHub.
7. Check versions, `dist-tags`, integrity and public metadata of the five. Their initial version has no OIDC provenance; later ones do.
8. Only with authorization, create and push `v1.8.0` on the same SHA, without delay: until then the five require a core `>=1.8` that is not on npm yet. The workflow publishes `@meekojs/meeko` with provenance, skips the five and creates the GitHub release. Skipping does not prove that a published tarball is identical, nor does it change its dist-tags.
9. Check all six with a clean installation outside the repository.

### Subsequent trusted publication

Update all six manifests, changelogs and compatibility ranges together. The tag must point to a commit on `main`. The `package-gates` job checks that, compares `v<version>` with **every** manifest, runs the gates, installs the tarballs in an external consumer and stores the six tarballs it will publish, after checking their name, their version and that `pnpm pack` resolved `workspace:*`. A version with a suffix uses `next`; a stable one uses `latest`.

The `publish` job is the only one with `id-token: write` and the `npm` environment, so its approval comes with the gates already green. It only receives those tarballs: it installs no dependencies and runs no project code. `scripts/publish-packages.ps1 -Trusted` checks all six versions before publishing the first one; only an HTTP 404 means one is missing, and it does not start if any package does not exist on npm yet. If a version already exists, it skips it to allow resuming. A published version is immutable: a fix requires another version. After a partial failure, keep the tag, review the real state and rerun the workflow once the cause is fixed. Nothing is published by a push to `main` or a pull request.

## Tags and targets

| Tag                   | Workflow               | Checks                            | Publishes                                                                                |
| --------------------- | ---------------------- | --------------------------------- | ---------------------------------------------------------------------------------------- |
| `v<versión>`          | `publish.yml`          | The six public manifests          | npm (all six public packages) and the GitHub release with the six VSIX files and the Chrome ZIP |
| `vscode-v<versión>`   | `publish-vscode.yml`   | `packages/vscode/package.json`    | Visual Studio Marketplace and Open VSX                                                   |
| `devtools-v<versión>` | `publish-devtools.yml` | `packages/devtools/manifest.json` | Chrome Web Store                                                                         |

`publish.yml` only triggers for tags starting with `v` and a digit (`v[0-9]*`): with `v*`, `vscode-v<versión>` also triggered it. Each workflow fails before publishing if the tag does not exactly match the version in its file. Extensions thus keep a version number independent of the npm package: an extension fix does not require publishing Meeko, and a Meeko version does not upload extensions to stores.

### npm package and prereleases

`publish.yml` publishes a version containing a hyphen, such as `1.0.0-rc.1`, with `npm publish --tag next`; `latest` stays unchanged. A version without a hyphen is published to `latest`. After a prerelease, check with `npm view @meekojs/meeko dist-tags` that `latest` still points to the latest stable version.

### GitHub release

When npm finishes, the `github-release` job in `publish.yml` packages the VSIX files for `win32`, `linux` and `darwin` in x64 and arm64 and the Chrome DevTools ZIP (with the `meeko-devtools/` folder) on Windows, calculates `SHA256SUMS.txt` and attaches them to the tag's release. If the version is a prerelease, the release is created as a prerelease; otherwise, it is marked as the latest. If the release already existed, for example created manually or by a previous attempt, only the attachments are replaced. It is the only job with `contents: write`; `id-token: write` is limited to the job running `npm publish`.

The attached VSIX files and ZIP correspond to each extension's own version at that commit. Their presence in the release does not imply that the version is on Marketplace, Open VSX or Chrome Web Store.

## Publishing to extension stores

The store workflows are configured but inactive: each publishing step checks whether its secret exists and, if missing, skips the step with a warning in the run summary instead of failing. The preceding tests always run.

Secrets are stored in **Settings → Secrets and variables → Actions → Repository secrets** in the `meekojs/meeko` repository, with the exact names in the following tables. They are not stored in the repository, in versioned `.env` files or in documentation.

### VS Code: Marketplace and Open VSX

`publish-vscode.yml` checks that `vscode-v<versión>` matches `packages/vscode/package.json` and the version is `major.minor.patch`; neither store accepts prerelease suffixes in the extension version. It then runs the extension's unit tests, the platform VSIX and the test in an isolated VS Code host on Windows, Ubuntu and macOS. Only if everything passes does it package the six VSIX files and publish them with `@vscode/vsce@4.0.0` and `ovsx@1.3.0`, both pinned versions. For Marketplace, `vsce publish --azure-credential` takes access from the session opened by `azure/login` with Entra ID; with the temporary PAT and on Open VSX, each tool reads its token from the environment variable. No token appears on the command line. `--skip-duplicate` allows rerunning if one store failed after the other published.

| Secret            | Usage                                                                                                                 |
| ----------------- | --------------------------------------------------------------------------------------------------------------------- |
| `AZURE_CLIENT_ID` | Application (client) ID of the Microsoft Entra ID registration that publishes to Marketplace. It is not a password.   |
| `AZURE_TENANT_ID` | Directory (tenant) ID of that registration. It is not a password.                                                     |
| `VSCE_PAT`        | Optional fallback for Marketplace if both Entra IDs are missing. The previous secret was deleted and its PAT revoked. |
| `OVSX_PAT`        | Open VSX token restricted to publishing `meekojs.meeko-language`.                                                     |

Visual Studio Marketplace publishing uses **Microsoft Entra ID** and OIDC: GitHub issues a short-lived token for the `vscode-marketplace` environment on each run, Entra exchanges it for Azure DevOps access and no token is stored. Global Azure DevOps PATs (those for **All accessible organizations**, the only scope Marketplace accepts) [are being retired on December 1, 2026](https://code.visualstudio.com/api/working-with-extensions/publishing-extension). The workflow retains the fallback path with `VSCE_PAT` if both Entra IDs are missing, but that secret is no longer configured.

Visual Studio Marketplace setup:

1. On the [Marketplace management page](https://marketplace.visualstudio.com/manage), with the maintainer's Microsoft account, create the publisher with ID `meekojs`, the same `publisher` value as in `packages/vscode/package.json` (it already exists).
2. In the [Azure portal](https://portal.azure.com/), **Microsoft Entra ID → App registrations → New registration**: name `meeko-marketplace-publisher`, accounts in this directory only, no redirect URI. An Azure subscription is not required. Note the **Application (client) ID** and **Directory (tenant) ID**.
3. In the registration, **Certificates & secrets → Federated credentials → Add credential**, scenario **GitHub Actions deploying Azure resources**: organization `meekojs` (ID `346854110`), repository `meeko` (ID `1430909739`), entity type **Environment**, environment `vscode-marketplace`. Check that the subject is `repo:meekojs@346854110/meeko@1430909739:environment:vscode-marketplace` and the audience is `api://AzureADTokenExchange`. GitHub issues the subject with immutable IDs in this repository; the format using only names does not match. Do not create a client secret.
4. In GitHub, save the two IDs as secrets `AZURE_CLIENT_ID` and `AZURE_TENANT_ID` (Settings → Secrets and variables → Actions).
5. Manually run the **Identidad de Marketplace** workflow (`marketplace-identity.yml`). Its summary shows the identity's Azure DevOps profile ID.
6. On the `meekojs` publisher page, **Members → Add**, paste that ID and assign it the **Contributor** role.
7. Run **Identidad de Marketplace** again: it must indicate that the identity can now publish. Then delete the `VSCE_PAT` secret and revoke the PAT in Azure DevOps.

Open VSX setup:

1. Sign in to [open-vsx.org](https://open-vsx.org/) with the project's GitHub account and accept the Eclipse Foundation publishing agreement from the profile.
2. Under **Settings → Access Tokens**, generate a token.
3. Create the `meekojs` namespace once from the Open VSX account (it already exists). To have the extension appear as verified, request ownership of the namespace following the Open VSX instructions.
4. Restrict the token to the `meekojs` namespace, the `meeko-language` extension and **Publishing only**. Save it as `OVSX_PAT`.

### Chrome Web Store

`publish-devtools.yml` checks that `devtools-v<versión>` matches `packages/devtools/manifest.json`. On Windows, it runs `pnpm run devtools:check` and the test with the extension installed in Chrome for Testing. It then packages a ZIP with `manifest.json` at the root, as the store requires (`package-zip.ps1 -RootLayout`), uploads it and submits it for review through the [Chrome Web Store API v2](https://developer.chrome.com/docs/webstore/using-api). API version 1.1 is deprecated; v2 identifies each item by publisher, so `CHROME_PUBLISHER_ID` is required. Publishing occurs only if all five secrets exist; with incomplete configuration, the job warns which names are missing and does not publish.

| Secret                 | Usage                                                                                                |
| ---------------------- | ---------------------------------------------------------------------------------------------------- |
| `CHROME_EXTENSION_ID`  | ID of the Meeko DevTools item in the store.                                                          |
| `CHROME_PUBLISHER_ID`  | Publisher ID, visible under **Publisher → Settings** in the developer dashboard.                     |
| `CHROME_CLIENT_ID`     | Google Cloud OAuth client ID.                                                                        |
| `CHROME_CLIENT_SECRET` | That OAuth client's secret.                                                                          |
| `CHROME_REFRESH_TOKEN` | Refresh token for the owner account with the `https://www.googleapis.com/auth/chromewebstore` scope. |

Setup:

1. Register the developer account in the [Chrome Web Store dashboard](https://chrome.google.com/webstore/devconsole) and pay the one-time registration fee.
2. The API only updates existing items: the first version is uploaded manually from the dashboard with the `package-zip.ps1 -RootLayout` ZIP, completing the listing, privacy policy and permission justifications. The ID assigned by the store is `CHROME_EXTENSION_ID`.
3. In [Google Cloud Console](https://console.cloud.google.com/), create a project and enable **Chrome Web Store API**.
4. Configure the OAuth consent screen as **External** and publish it to production. If left in testing mode, Google expires the refresh token after seven days.
5. Under **Credentials → Create credentials → OAuth client ID**, create a **Web application** client with `https://developers.google.com/oauthplayground` as an authorized redirect URI. You will obtain `CHROME_CLIENT_ID` and `CHROME_CLIENT_SECRET`.
6. In [OAuth Playground](https://developers.google.com/oauthplayground), select **Use your own OAuth credentials** with that client, authorize the `https://www.googleapis.com/auth/chromewebstore` scope with the extension owner's account and click **Exchange authorization code for tokens**. The `refresh_token` value is `CHROME_REFRESH_TOKEN`.
7. Copy the publisher ID from **Publisher → Settings** as `CHROME_PUBLISHER_ID`.

The store reviews each submission; the workflow ends when the upload is accepted and the submission is under review, not when the version is public. If visibility was changed in the dashboard, publish manually once before using the API again.

### Publish an extension version

1. Bump the version in `packages/vscode/package.json` and its `CHANGELOG.md`, or in `packages/devtools/manifest.json` and `package.json`.
2. After checking that CI passed on `main`, create the `vscode-v<versión>` or `devtools-v<versión>` tag on that commit and push it.
3. Review the run: steps skipped due to missing secrets appear as warnings. Then check the version in each store.

The [npm `1.7.1`](https://www.npmjs.com/package/@meekojs/meeko/v/1.7.1) package will come from commit `PENDIENTE: hash del commit publicado` (pending: published commit hash) and will match tag [`v1.7.1`](https://github.com/meekojs/meeko/releases/tag/v1.7.1). It is a patch on `1.7.0` with the changes recorded in the [CHANGELOG](../../packages/meeko/CHANGELOG.md):

- **`localhost` in the displayed URL.** `meeko dev`, `meeko start`, `meeko preview`, the Node, Bun and Deno outputs and the `meeko init` `server.mjs` write `http://localhost:4173` instead of `http://127.0.0.1:4173` when listening on loopback or all interfaces; with `0.0.0.0` or `::`, they add network addresses. The listening address does not change.
- **`model` on a checkbox with `boolean | undefined`.** The `useForm` field for a key such as `v.optional(v.boolean(), false)` has the input type, `boolean | undefined`, and `model` on an `<input type="checkbox">` rejected it with `TS2322`; it now accepts it and treats `undefined` as unchecked. The field retains the input type because typing it with the output would break schemas whose input really accepts `undefined`; a checkbox field component declares `FormField<boolean | undefined>`.
- **`meeko dev` without an editor bridge.** With `MEEKO_EDITOR_BRIDGE=0`, `meeko dev` did not publish the descriptor or warn, and the extension left “Meeko live” disconnected without explanation. It now writes `Valores en vivo del editor desactivados (MEEKO_EDITOR_BRIDGE=0)` after the URL (editor live values disabled; or the reason if listening outside loopback), records it in `.meeko/dev/server.json` (`editorBridge: false`, `editorBridgeReason`) and the extension shows “Meeko live: desactivado en meeko dev” (disabled in meeko dev).
- **No console windows on Windows.** The language server opened a console window every few seconds while editing a `.meeko`: `framework/page-contracts-check.ts` and `framework/check-project.ts` (two calls) launched `typescript/bin/tsc` with `node`, the JavaScript launcher, which opens `tsc.exe` without `windowsHide`. The four compiler calls (also the one in `check.ts`) now go through `tscCommand` in `src/typescript-cli.ts`, which executes `tsc.exe` directly on Windows and uses the launcher on other systems; `tests/typescript-cli.test.ts` fails if another `src` file references `bin/tsc` again.
- **A native form's `return` field.** An unencoded `return=/formularios` appeared to return to `/`. It was not a Meeko failure: when testing with `curl` from Git Bash, MSYS converts the argument to `return=C:/Program Files/Git/formularios`, which is rejected as a foreign scheme. A test establishes that the unencoded path, encoded path, `multipart/form-data` and same-origin absolute URL return to the page, and hostile paths still return to `/`; the guide explains this.

The VS Code extension moves to `1.7.1` because its bundled language server changed (the checkbox `model` type and checks without console windows) and “Meeko live” shows a `meeko dev` started without a bridge. Meeko DevTools remains at `1.0.0`. There are no breaking changes.
